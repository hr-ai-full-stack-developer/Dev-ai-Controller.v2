# Dev’ai Controller v2 — Deployment and Operations Guide

Repository: `hr-ai-full-stack-developer/Dev-ai-Controller.v2`

## What is actually deployed

The production target is one Cloudflare Worker named `devai-controller`.

- `worker/index.ts` is the Cloudflare entrypoint.
- `server/app.ts` is the shared Express API used by Cloudflare and local Node.
- `server.ts` is the local/standalone Node entrypoint.
- `src/` contains the React operator UI.
- `dist/` contains browser assets generated by Vite.
- `build/server.cjs` is the standalone Node build and is never served as a static asset.
- `tests/` contains API integration tests.
- `wrangler.toml` is the authoritative Cloudflare binding/configuration file.

Do not treat architecture proposals in historical documents as deployed infrastructure. The current Wrangler file binds Workers AI and static assets. D1, KV, R2, Vectorize, Durable Objects and cron triggers are not production bindings until they are explicitly added to `wrangler.toml` and implemented in code.

## Required runtime secrets

Configure these on the Worker:

- `ADMIN_EMAIL` — operator login email.
- `ADMIN_PASSWORD` — strong operator password.
- `ADMIN_JWT_KEY` — high-entropy session/TOTP signing key (32+ random bytes recommended).

The server fails closed when credentials are absent. `ADMIN_WJT_KEY` is accepted only as a temporary legacy alias and should not be newly configured.

Optional integrations:

- `GITHUB_TOKEN` — repository inspection and draft PR operations.
- `EMAIL_FORWARD_TO` — verified destination for inbound Cloudflare Email Routing forwarding.
- `OPENAI_API_KEY` — optional AI fallback.
- `GEMINI_API_KEY` — optional provider integration.
- `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` — optional legacy persistence for token/audit records.
- `WORKER_SECRET` — encryption seed for stored provider credentials.

Workers AI uses the `AI` binding and does not need a browser-exposed API key.

### Transactional email and routing

Outbound transactional mail uses the Cloudflare `EMAIL` send binding. The sender is fixed in code to `Operava <noreply@internal.operavaglobal.com>`. Workers AI may create or refine message content, but Cloudflare Email Service is the actual mail transport. The application does not claim success unless Email Service accepts the message.

The Worker also implements an inbound `email()` handler. Configure Cloudflare Email Routing to send the intended OPERAVA address to this Worker, and verify `EMAIL_FORWARD_TO` as a destination before enabling the rule. Cloudflare Email Sending requires `internal.operavaglobal.com` to be onboarded separately as an Email Sending subdomain before this sender can deliver mail.

Branded email endpoints include public administrator email-OTP request/verification and an authenticated transactional update endpoint. OTP requests are restricted to the configured administrator email and throttled per Worker isolate.

## GitHub Actions deployment

Repository Actions secrets:

- `CLOUDFLARE_API_TOKEN`
- `CLOUDFLARE_ACCOUNT_ID`
- `ADMIN_EMAIL`
- `ADMIN_PASSWORD`
- `ADMIN_JWT_KEY`

The main-branch deploy job provisions the three admin values as Cloudflare Worker secrets before deploying. They are never written to `wrangler.toml` or the browser bundle.

On pull requests, `.github/workflows/deploy.yml` installs from the lockfile, typechecks, runs API tests, builds the web client and performs a Wrangler dry run. On `main`, deployment runs only after verification succeeds and after both Cloudflare deployment credentials are present.

## Cloudflare setup

1. Authenticate Wrangler to the intended Cloudflare account.
2. Configure `ADMIN_EMAIL`, `ADMIN_PASSWORD`, and `ADMIN_JWT_KEY` with `wrangler secret put`.
3. Configure optional provider secrets only for features you intend to use.
4. Verify the Workers AI `AI` binding and Cloudflare `EMAIL` send binding in `wrangler.toml`.
5. Onboard `internal.operavaglobal.com` in Cloudflare Email Service for Email Sending, then create the intended Email Routing rule to this Worker with a verified `EMAIL_FORWARD_TO` destination.
6. Add GitHub Actions deployment credentials to repository secrets.
7. Merge only after PR verification is green.
8. Verify `/api/health` and `/api/auth/readiness`; readiness must report all three auth fields configured.
9. Sign in, verify `/api/auth/verify-session`, request a test email OTP, and inspect the authenticated dashboards.

## Security invariants

- No production secret belongs in `src/`, `public/`, Vite variables, or committed environment files.
- Private `/api/*` and `/v1/*` routes require the validated operator session except explicitly public routes.
- Cross-origin state-changing admin requests are rejected.
- Browser sessions use HTTP-only cookies; bearer tokens remain supported for API clients.
- The repository contains no seeded “successful deployment/email/database” activity. Operational history must originate from real requests or a real persistence backend.

## Persistence and capability boundaries

Today, chat sessions and several agent/automation registries use process memory. They can disappear when a Worker isolate restarts. Supabase support is optional and currently covers selected token/audit paths rather than every application record.

Therefore, do not claim durable scheduling, durable chat history, D1-backed state, R2 knowledge storage, Vectorize retrieval, KV sessions, Durable Object orchestration, or cron execution until those bindings and implementations exist.

Password recovery and autonomous scheduled execution intentionally return unavailable responses rather than pretending an action occurred.

## Post-deployment smoke test

1. `GET /api/health` returns 200.
2. Anonymous access to a private endpoint such as `GET /api/deployments` returns 401.
3. Valid operator credentials establish an HTTP-only session.
4. `GET /api/auth/verify-session` confirms the authenticated session.
5. Authenticated registry endpoints return JSON.
6. Unknown API routes return JSON 404 and never fall through to the SPA.
7. Test every configured external provider from the status UI; an unconfigured provider must be reported as unavailable, not healthy.

## Rollback

Use Cloudflare deployment/version rollback for a deployed Worker. The dashboard deployment controls can only operate when the Cloudflare API credentials have the required permissions. They do not build arbitrary GitHub source.

## Definition of production-ready

A commit is release-ready only when: GitHub verification is green; required Worker secrets exist; the intended Cloudflare account is confirmed; the deployment job succeeds; and the post-deployment smoke test passes. Repository code alone cannot prove account-side secrets or a live deployment.
